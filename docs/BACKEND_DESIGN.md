# バックエンド設計書

## 1. 文書の目的

本書は、iOS／Android向けタイムカプセル日記アプリを支えるバックエンドの論理設計を定義する。
DDDとOnion Architectureを採用し、現在のコードの追認ではなく、確定した業務ルールを実現するための設計とする。

## 2. アーキテクチャ方針

開発初期は単一デプロイ可能なモジュラーモノリスとする。サービス分割を先行させず、境界づけられたコンテキストと依存方向をコード上で明確にする。

```text
API / Presentation
        ↓
Application
        ↓
Domain
        ↑
Infrastructure
```

- Domainは他レイヤーへ依存しない。
- Applicationはユースケースとポートを定義する。
- InfrastructureはDB、ストレージ、JWT、メール、通知、課金確認を実装する。
- APIはHTTP、認証、入力形式、Problem Detailsへの変換を担当する。

## 3. モジュール境界

| モジュール | 責務 |
| --- | --- |
| Identity | ユーザー登録、ログイン、トークン更新、パスワード再設定 |
| Profiles | 表示名、言語、タイムゾーン |
| Anniversaries | 記念日の設定、変更制限、変更履歴 |
| Posts | 投稿枠、メディア、10分間の取消、解禁、カレンダー取得 |
| Subscriptions | Premium権限、月額／年額のストア購入情報の検証 |
| Notifications | 解禁通知、端末トークン、配信履歴 |
| Media | 保存先抽象化、アップロード、削除、孤立ファイル回収 |

初期段階では同一プロセス・同一PostgreSQLを利用するが、モジュール間はApplicationの公開インターフェースを経由する。

## 4. ドメインモデル

### 4.1 User集約

主な属性：

- UserId
- Email
- PasswordHash
- DisplayName
- PreferredLanguage
- TimeZoneId
- Status
- CreatedAt

主なルール：

- メールアドレスは正規化した値で一意とする。
- ユーザーの現地日付は登録済みIANAタイムゾーンからサーバーが算出する。
- クライアントが投稿対象日を指定することはできない。

### 4.2 Anniversary集約

主な属性：

- AnniversaryId
- UserId
- Name
- Month
- Day
- EffectiveFrom
- EffectiveTo
- ChangedAt

主なルール：

- ユーザーが同時に有効にできる記念日は最大1件。
- 初回設定または前回変更から14日経過するまで再変更できない。
- 現在の記念日当日は変更できない。
- 新しい記念日にユーザーの現地日付と同じ月日を指定できない。
- 変更はトランザクション完了時から即時反映する。
- 2月29日の記念日は、うるう年でない年には2月28日を記念日当日として扱う。
- 履歴は削除せず、有効期間を保持する。

記念日変更時には、旧設定に基づく未解禁の第2投稿を非表示対象へ変更する。一方、変更時点ですでに解禁済みの第2投稿は維持する。

### 4.3 Post集約

主な属性：

- PostId
- UserId
- OccurredOn
- UnlockOn
- DailySequence（1または2）
- AnniversarySettingId（通常日はnull）
- Message
- MediaType
- StorageKey
- Status
- SuppressionReason
- CreatedAt
- CancelableUntil

主なルール：

- 通常日は `DailySequence = 1` の1件だけ登録できる。
- 有効な記念日は `DailySequence = 1, 2` の2件まで登録できる。
- 1投稿につき写真または動画を1ファイルだけ持つ。
- 無料会員は写真のみ登録できる。
- 有料会員は写真または最大60秒・100MBの動画を登録できる。
- `OccurredOn` はユーザーの現地日付をサーバーが決定する。
- `UnlockOn` は原則 `OccurredOn` の1年後とする。
- 2月29日の投稿は、翌年がうるう年でなければ2月28日に解禁する。
- 投稿後10分以内だけ取り消せる。
- 取り消し済み投稿は当日の投稿数に含めない。
- 取り消し期限後は、解禁まで投稿内容を取得できない。
- 解禁後は期限なく閲覧できる。

### 4.4 Subscription集約

- Free：写真投稿のみ
- Premium：写真または動画投稿
- 月額ベースプランは月額300円、年額ベースプランは年額3,000円とし、利用できる機能は同一とする。
- Premiumの動画制限：最大60秒かつ100MB
- 無料トライアルは提供しない。
- 権限判定は投稿作成時にサーバーで行う。
- iOS／Androidのストア購入情報を検証し、有効期限と状態を保持する。
- クライアントから送られた `isPremium` は信用しない。
- 月額と年額は同じPremium商品内の別ベースプランとして扱う。

## 5. 記念日変更処理

記念日変更は以下を1トランザクションで処理する。

1. ユーザー行または記念日管理行をロックする。
2. ユーザーの現地日付を算出する。
3. 当日変更禁止と14日制限を確認する。
4. 現在の記念日履歴を終了する。
5. 新しい記念日履歴を即時有効化する。
6. 旧記念日設定に紐づく第2投稿を検索する。
7. `UnlockOn` が現地の今日より後の投稿を `AnniversaryChangedBeforeUnlock` として非表示対象にする。
8. `UnlockOn` が現地の今日以前の投稿は変更しない。
9. 影響件数と次回変更可能日時を返す。

これにより、変更前にカレンダーへ表示済みの2件は維持され、まだ表示されていない2件目だけが将来非表示になる。非表示対象のメディアとレコードは物理削除しない。

## 6. 投稿作成処理

1. JWTからUserIdを取得する。
2. ユーザーのタイムゾーンから現地日付を算出する。
3. 有効な記念日と会員権限を取得する。
4. メディア種別、MIMEタイプ、容量、動画時間を検証する。
5. 当日の有効な投稿件数をDB上で確認する。
6. 記念日なら上限2件、通常日なら上限1件として採番する。
7. メディアを保存し、公開URLではなく `storage_key` を取得する。
8. PostをDBへ保存する。
9. `cancelableUntil` と解禁日だけを返す。

同時送信による上限超過は、DB一意制約とトランザクションで防止する。ストレージ保存後にDB保存が失敗した場合は補償削除を試み、失敗時は孤立ファイル回収対象として記録する。

## 7. 閲覧制御

APIは認証済みユーザー本人の投稿だけを返す。PostIdを指定した場合も必ずUserId条件を含める。

カレンダーに返せる条件は以下のすべてを満たす投稿とする。

- `status = Active`
- `unlock_on <= ユーザーの現地日付`
- `suppression_reason IS NULL`
- `user_id = 認証ユーザーID`

未解禁投稿に対しては、本文、StorageKey、署名付きURL、メディア種別を返さない。投稿済み状態を表示する専用APIは、日付、件数、取消期限など必要最小限の情報だけを返す。

## 8. API設計

ベースパスは `/api/v1` とする。

### 8.1 Identity

| Method | Path | 用途 |
| --- | --- | --- |
| POST | `/auth/register` | ユーザー登録 |
| POST | `/auth/login` | ログイン |
| POST | `/auth/refresh` | リフレッシュトークンのローテーション |
| POST | `/auth/logout` | セッション失効 |
| POST | `/auth/password-reset/request` | 再設定要求 |
| POST | `/auth/password-reset/confirm` | パスワード更新 |

### 8.2 Profile／Anniversary

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/me` | プロフィール取得 |
| PATCH | `/me` | 表示名、言語、タイムゾーン更新 |
| GET | `/me/anniversary` | 現在設定と次回変更可能日取得 |
| PUT | `/me/anniversary` | 初回設定または変更 |
| GET | `/me/anniversary/change-impact` | 変更時に非表示となる未解禁投稿数 |

### 8.3 Posts／Calendar

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/posts/today/status` | 当日の投稿枠と取消可能状態 |
| POST | `/posts` | 投稿作成 |
| DELETE | `/posts/{postId}` | 10分以内の取り消し |
| GET | `/calendar?year=&month=` | 月ごとの解禁済み投稿概要 |
| GET | `/calendar/{date}` | 指定日の解禁済み投稿詳細 |
| GET | `/media/{postId}` | 認可後のメディア取得または短期署名URL発行 |

### 8.4 Subscription／Device

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/me/subscription` | 現在の権限取得 |
| POST | `/subscriptions/verify` | ストア購入検証 |
| POST | `/devices` | プッシュ通知トークン登録 |
| DELETE | `/devices/{deviceId}` | 端末登録解除 |

## 9. 認証とセキュリティ

- アクセストークンは短寿命JWTとする。
- リフレッシュトークンは毎回ローテーションし、ハッシュ化してDBに保存する。
- 再利用された旧リフレッシュトークンを検知した場合は、同一トークンファミリーを失効する。
- パスワードはArgon2id等の適切なアルゴリズムでハッシュ化する。
- メディアは公開バケットへ置かず、認可後に短期署名URLまたはAPIストリームで提供する。
- DBには公開URLではなく移行可能な `storage_key` を保存する。
- 監査ログにパスワード、トークン、投稿本文、署名URLを記録しない。
- レート制限をログイン、パスワード再設定、アップロードへ適用する。
- アカウント削除は再認証を要求し、猶予期間後に個人データを削除する。

## 10. エラー形式

RFC 9457 Problem Detailsを使用する。

```json
{
  "type": "https://example.com/problems/post-limit-reached",
  "title": "Post limit reached",
  "status": 409,
  "detail": "No more posts can be created today.",
  "code": "POST_DAILY_LIMIT_REACHED",
  "traceId": "..."
}
```

クライアントが安定して翻訳できるよう、機械判定用の `code` を必須とする。入力エラーはフィールド別エラーを拡張メンバーとして返す。

## 11. 日時設計

- 永続化する瞬間はUTCとする。
- ユーザーの暦日は `date` 型とIANAタイムゾーンで扱う。
- `OccurredOn` は投稿時点で確定し、後からタイムゾーンを変更しても書き換えない。
- 解禁判定、記念日当日、1日上限はユーザーの登録タイムゾーンを基準とする。
- タイムゾーン変更を上限回避に利用できないよう、短期間の連続変更を監査・制限できる設計にする。

## 12. バックグラウンド処理

- 解禁通知の予約・送信
- 失敗した通知の再試行
- 孤立メディアの回収
- 取り消し済みメディアの遅延削除
- 期限切れリフレッシュトークンの削除
- ストア購読状態の定期照合

ジョブは冪等にし、同じ処理が複数回実行されても重複通知や誤削除が起きないようにする。

## 13. テスト方針

- Domain：通常日／記念日の上限、14日制限、当日変更禁止、2月29日、10分取消
- Application：記念日変更時の解禁済み・未解禁投稿の分岐
- Infrastructure：DB一意制約、トランザクション、R2障害、補償削除
- API：認証、UserId分離、Problem Details、言語ヘッダー
- 境界値：10分ちょうど、現地0時、夏時間、解禁日当日、同時投稿
- セキュリティ：他ユーザーのPostId指定、期限切れURL、リフレッシュトークン再利用

## 14. 将来拡張

共有機能を追加する場合もPost集約の公開状態を直接拡張せず、Sharingモジュールで共有相手、同意、公開範囲を管理する。初期リリースでは共有APIを公開しない。

メモリー動画は初回リリースで販売、申込受付、生成を行わない。外部アンケートでは需要調査だけを行い、バックエンドは回答、メールアドレス、予算、メディアを取得しない。将来販売する場合は、課金、個人情報、運用体制を再設計する。
